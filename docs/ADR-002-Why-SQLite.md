# ADR-002: 为什么选择 SQLite 而非 PostgreSQL

## 状态
已接受

## 背景
v2.1 版本需要为扫描历史、补丁记录、对抗历史增加持久化存储。
需要选择数据库方案。

## 考虑的方案

### 方案 A: SQLite
- **优点**：零配置、零运维、无独立服务进程、文件级持久化、与 Python 标准库集成（sqlite3）、无网络依赖
- **缺点**：单写入并发有限（写锁）、无内置网络访问（但 FastAPI 已提供 HTTP API）、不适合多进程并发写入

### 方案 B: PostgreSQL
- **优点**：真正的高并发、支持网络访问、关系型完整性保证、有连接池支持
- **缺点**：需要独立安装和配置、需要额外的连接池管理（如 SQLAlchemy）、部署复杂度显著增加

### 方案 C: 直接使用 JSON 文件
- **优点**：零依赖、零运维
- **缺点**：无查询能力、并发写入冲突、无事务保证、无索引

## 决策
**选择方案 A: SQLite**

## 理由
1. **零运维**：无需安装数据库服务，`import sqlite3` 即可使用
2. **文件级持久化**：数据库就是一个 `.db` 文件（`./data/assessment.db`），备份/迁移极简
3. **满足规模**：单用户场景，扫描历史 < 10,000 条，SQLite 完全足够
4. **与现有架构契合**：FastAPI 提供 HTTP API 作为访问接口，不需要直接网络访问数据库
5. **教学友好**：学生可以直观地查看数据库文件，不需要启动数据库服务

## 后果

**正面**：
- 部署极其简单：无需安装 PostgreSQL/MySQL
- 故障恢复简单：`.db` 文件损坏概率低，备份即复制文件
- 成本为零：无数据库软件许可或云资源费用

**负面**：
- 多用户并发写入可能产生锁（但对于教学演示场景，几乎不会发生）
- 未来扩展为多用户系统时需要迁移到 PostgreSQL
- 无内置数据可视化工具（但通过 API 提供数据，可接入前端）

## 升级路径
当系统需要支持多用户并发写入时，可平滑迁移到 PostgreSQL：
1. 安装 PostgreSQL
2. 修改 `database.py` 中的连接字符串（SQLAlchemy 支持 SQLite → PostgreSQL 的少量改动）
3. 执行数据迁移脚本
