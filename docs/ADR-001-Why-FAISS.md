# ADR-001: 为什么选择 FAISS 作为 RAG 向量数据库

## 状态
已接受

## 背景
在 v2.0 ~ v2.2 版本迭代中，我们需要为 RAG（检索增强生成）知识库选择向量数据库，
用于实现漏洞语义相似度检索（替代简单的关键词匹配）。

## 考虑的方案

### 方案 A: FAISS（Facebook AI Similarity Search）
- **优点**：纯 Python API、单机即可运行、无需独立服务进程、支持 GPU 加速（可选）、与 NumPy/Python 生态无缝集成
- **缺点**：分布式扩展性有限、无内置认证/访问控制、需手动管理索引持久化

### 方案 B: Chroma（专用向量数据库）
- **优点**：专为 LLM 应用设计、支持元数据过滤、提供 Python 客户端、有持久化
- **缺点**：需要独立的 Chroma Server 进程（额外资源占用）、Python 客户端尚在快速迭代中

### 方案 C: Pinecone（云服务向量数据库）
- **优点**：云原生、分布式、高可用、无需运维
- **缺点**：需要 API Key 和网络连接、不适合内网/离线部署、有使用成本

### 方案 D: 纯关键词匹配（Dict）
- **优点**：零依赖、零延迟
- **缺点**：无语义能力，无法识别"SQL注入"和"数据库攻击"的语义相似性

## 决策
**选择方案 A: FAISS**

## 理由
1. **零运维**：FAISS 是库而非服务，不需要启动独立进程，不会增加部署复杂度
2. **教学友好**：学生可以在一台机器上直接运行，无需配置额外的数据库服务
3. **性能足够**：对于 ~100 条知识库条目（4个CVE × 若干案例），FAISS 的 IndexFlatIP 性能完全足够
4. **成本为零**：无需第三方服务或云资源
5. **团队熟悉度**：团队已有 NumPy 使用经验，学习曲线平缓

## 后果
**正面**：
- 部署极其简单：`pip install faiss-cpu` 即可
- 对靶机网络环境无依赖（内网可运行）
- 索引构建和查询性能满足教学场景需求

**负面**：
- 水平扩展性差（但对于当前规模不需要）
- 无内置增量更新机制（需手动重建索引，或使用 IVFFlat/HSNW 等索引类型）
- 无访问控制（但因部署在本地，风险可控）

## 未来可考虑
- 若知识库规模超过 10,000 条，升级为 Chroma 或 Milvus
- 若需要增量索引，切换到 FAISS IVF 系列索引
